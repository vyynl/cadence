# Phase 2b — Cloud Sync (implementation plan)

> **Status: 2b-2/2b-3 implemented; 2b-4a complete; 2b-4b next.** Server scaffold, auth,
> Git object transfer, node push/pull, cursor pulls, the shared `NodeCodec`,
> the daemon `SyncLedger`/`SyncClient`/`Sync`/`SyncWorker`, and
> `POST /sync/projects` are in place. Remaining 2b-4 work: daemon preference
> push/apply, partial batches, and the Phoenix Channels notification
> accelerator. This document remains the cold-start brief for the remaining
> milestones. The canonical contract is `docs/spec.md` (especially §5, §10,
> §12, §13).

Phase 2b delivers the local↔cloud sync path: a Phoenix server that stores a
project's DAG, token-authenticated push/pull endpoints, and the daemon's sync
ledger + client. It is what makes "work on machine A, resume on machine B"
(§1 use case 4) real.

---

## 1. Scope

**In scope**
- Manual Phoenix scaffold for `cadence_server` (no `mix phx.new`), Postgres
  `Repo`, endpoint, PubSub.
- Bearer-token authentication for daemons via AshAuthentication API keys;
  OAuth (GitHub/Google) for humans; token issuance is the OAuth-session-guarded
  `POST /auth/tokens` endpoint.
- Git **object transfer** between daemon and server (new `GitStore` API).
- Sync endpoints: `POST /sync/nodes`, `GET /sync/nodes?since=`, and the
  preferences channel (`POST /sync/preferences`).
- Daemon `SyncLedger` + `SyncClient`, wired into the commit pipeline and boot
  rehydration.
- Conflict handling per §10.4 (a pushed node becomes a sibling).
- Server PubSub broadcast on writes (§10.2) — clients may ignore it until later.

**Out of scope (later phases)**
- Union/meld and proposals (§6.5/§6.6, Phase 4).
- Web UI / LiveView (Phase 3) — the server scaffolds Phoenix but no views yet.
- Sync object negotiation so clients don't re-push known objects (§13 Phase 7).
- Doc automation, Docker actions.
- Multi-user conflict *UX* (§16).

## 4. Authentication — implemented in 2b-1

- **Daemons** authenticate with `Authorization: Bearer <api-key>`.
  `Cadence.ServerWeb.AuthPlug` wraps
  `AshAuthentication.Strategy.ApiKey.Plug`, which validates the key and assigns
  the owning user (and Ash actor). Invalid/missing/expired/revoked keys get a
  JSON 401.
- **Humans** sign in with AshAuthentication OAuth (GitHub and Google). Routes
  are generated by `AshAuthentication.Phoenix.Router.auth_routes/3`; the
  `AuthController` stores the session and redirects to `/auth/tokens/new`.
- **Issuance** is the OAuth-session-guarded `POST /auth/tokens` endpoint.
  `Cadence.Server.Accounts.create_api_key/2` creates an AshAuthentication API
  key; the plaintext is rendered once and only its hash is stored.
- Endpoints scope every read/write to projects the user is a member of
  (`Membership` role `owner`/`trusted`) — enforced as sync endpoints land.

Resolved decisions: token issuance is OAuth-guarded (no CLI/seeded token);
keys are per-user. Project scoping is enforced per request in 2b-2.

## 5. Data model & migrations (server)

- `projects`, `nodes`, `memberships` — same columns as the daemon migration,
  Postgres types, `parents uuid[]` + GIN index, unique `projects.slug`.
- `users` (AshAuthentication) + `tokens` (hashed personal access tokens).
- **Sync bookkeeping** (server-only): a monotonic cursor for pulls.
  **Resolved:** option 1 — a `nodes.seq bigserial` column (indexed). It is
  Postgres-specific, so it stays out of the shared `Node` schema. The other
  options (`(inserted_at, id)` tuples, `sync_events`) are not used.
- Resolved in 2b-2: the daemon's node UUID **is** the cloud ID (identity
  mapping), so no separate local→cloud table is needed and retries are
  idempotent.

## 6. Git object transfer (shared) — implemented in 2b-2

Added to `Cadence.Shared.GitStore`:
- `objects_from/2` → `{:ok, [%{sha, type, data}]}` for the commit plus every
  reachable tree/blob (depth-first, deduplicated by SHA).
- `import_objects/2` → validates SHA/type/payload (including tree-entry safety
  and commit structure) before writing; idempotent and content-addressed.
- `write_raw/3` (raw payload writer) and `has_object?/2`.

Wire format: `%{sha, type, data}` where `data` is `Base.encode64(payload)` and
`payload` excludes Git's `<type> <size>\0` header. The receiver reconstructs
the header and verifies the SHA. Phase 7 adds an existence handshake so clients
stop re-pushing; for 2b, send all objects per node (dedup by the store).

## 7. Daemon: ledger + client

> Detailed cold-start notes for 2b-3 live in `docs/phase-2b-3-prep.md`.

New modules (spec §5.2):
- `Cadence.Daemon.SyncLedger` (GenServer, persistent): per-project pull cursor and
  the `local_node_id ↔ cloud_node_id` mapping. Backed by SQLite (new table
  `sync_ledger`, or nullable `cloud_id` on `nodes` + a `sync_cursors` table).
  Rehydrates pending work on boot.
- `Cadence.Daemon.SyncClient` (`Req`): push/pull with bearer token, timeouts, and
  retry/backoff; reads `CAD_SERVER_URL` / `CAD_AUTH_TOKEN`.
- `Cadence.Daemon.Sync` context: `push_pending/1`, `pull/1`, `sync/1`
  (best-effort, offline-tolerant).

Integration:
- After a successful local commit, enqueue the node for push (async; never block
  the commit). A node with `cloud_id == nil` is pending.
- On pull, import remote nodes' Git objects into the local store, insert sibling
  `Node` rows, and update membership prefs (§10.5).
- Boot: `SyncLedger.rehydrate/0` flushes pending pushes and resumes the cursor.

## 8. Endpoints & payloads

All JSON, matching the existing `Cadence.Shared.Sync.*` structs (§10.6).

- `POST /sync/nodes` — body `%{nodes: [%{local_id, git_objects, metadata}]}`
  (`PushNodes`). Server: verify `owner`/`trusted` membership, enforce one
  project per batch, import/validate objects, insert nodes (local UUID = cloud
  ID), broadcast, respond with identity `mappings`.
- `GET /sync/nodes?project_id=<uuid>&since=<cursor>` —
  (`PullNodes`/`PullNodesResponse`) returns project nodes after the `nodes.seq`
  cursor, plus a new cursor; capped by `CAD_SYNC_PULL_LIMIT`.
- `POST /sync/preferences` — `%{project_id, active_heads, session_pointer}`
  (`PushPreferences`); upserts the caller's `Membership`. Pulled as part of the
  node pull response or a companion endpoint (open decision).
- `GET /health`.

Error semantics: 401 unauthenticated; 403 not an `owner`/`trusted` member; 404
unknown project; 400 malformed cursor; 409 node-ID conflict/duplicate; 422
malformed metadata, mixed projects, unknown/out-of-order parent, or invalid
objects. Batches are fail-fast (no partial node inserts).

**Conflict handling (§10.4):** if the cloud already has a child of the same
parent, the pushed node simply becomes a sibling — no merge, no rejection.

## 9. Data-flow walkthroughs

- **Offline commit → reconnect:** commit is local and durable; node queued in the
  ledger; on reconnect `SyncClient.push_pending` sends it; server returns a
  cloud id; ledger records the mapping.
- **Machine B resume:** B pulls since its cursor, imports objects, inserts nodes;
  pulls the user's preferences and moves its session pointer (§10.5).
- **Same-parent divergence:** A and B both spawn from `parent`; whichever pushes
  second lands as a sibling; the DAG absorbs it (no “branch” concept).

- **shared:** `GitStore.objects_from/2` + `import_objects/2` round-trip on a temp
  store (import into an empty store, assert equivalence); `write_raw/3`.
- **server:** `Phoenix.ConnTest` for `/sync/*` — auth rejection (401), non-member
  (403), push→pull round-trip, sibling/conflict case, preferences upsert.
  Postgres via a test database (`CAD_TEST_DATABASE_URL`, default
  `ecto://postgres:postgres@localhost:55432/cadence_test` in `config/test.exs`);
  AshAuthentication flows covered at the resource level (no live OAuth).
  Ephemeral test DB:

  ```bash
  docker run --rm -d --name cadence-test-pg \
    -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=cadence_test \
    -p 55432:5432 postgres:16-alpine
  mix test apps/cadence_server/test
  ```
- **daemon:** `Bypass` to stub the server; `SyncClient` retry/backoff;
  `SyncLedger` persistence + rehydrate; end-to-end local commit → push → pull as
  a sibling. No test hits a real server or LLM.

## 13. Risks / open decisions

- ~~**Token issuance** for daemons~~ — resolved in 2b-1: OAuth-gated
  `POST /auth/tokens`, AshAuthentication API keys, hashed at rest.
- ~~**Cursor representation**~~ — resolved in 2b-1: `nodes.seq bigserial`.
- **Ash policies / SAT solver:** server Ash resources currently rely on
  controller-level authorization rather than `Ash.Policy.Authorizer`, to avoid
  adding `picosat_elixir`/`simple_sat`. Revisit when the web UI calls Ash
  actions directly. See spec §16.
- **LiveView dependency:** `ash_authentication_phoenix` pulls
  `phoenix_live_view` transitively, although 2b-1 defines no LiveViews. No UI
  scope creep intended; Phase 3 still owns the web UI.
- ~~**Batch semantics / parent resolution**~~ — resolved in 2b-2: fail-fast,
  single-project, parents-first, at most one parent per pushed node (melds stay
  server-side). Unknown/out-of-order parents return 422.
- **Project provisioning gap:** 2b-2 assumes server `Project`/`Membership` rows
  already exist and that project IDs match the daemon. A real registration path
  (web UI, CLI, or sync endpoint) is still needed before live end-to-end sync.
- **Preferences transport**: folded into the node pull response vs. its own
  endpoint/cursor.
- **Object payload size**: base64 inflates by ~33%; `CAD_SYNC_PULL_LIMIT` bounds
  node count, not bytes. Consider object/body caps and Phase 7 negotiation.
- **Auth scope**: per-user tokens; project scoping is enforced per request.

Update spec §16 with the durable ones once decided.
